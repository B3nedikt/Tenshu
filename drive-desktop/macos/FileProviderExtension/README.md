# FileProviderExtension — Tenshu Drive File Provider (macOS, Phase 2)

A headless `NSFileProviderReplicatedExtension` (`.appex`) that puts Tenshu Drive
in Finder's *Locations* sidebar (under `~/Library/CloudStorage/`) with
download-on-open materialisation. It is a thin client of the **Control daemon**:
every list / metadata / fetch is a JSON call over the group-container Unix socket
(`docs/proposals/desktop-macos-integration.md` §5). Read-only in Phase 2; the
write path is Phase 3.

## Files

- `BridgeClient.swift` — synchronous JSON bridge client over the
  group-container UDS (a copy of the tray's client). It finds the container from the
  Team ID in its **own code signature** — a sandboxed extension has no environment to read.
- `FileBridge.swift` — typed wrappers for the daemon's methods (`control-shared`'s
  `ControlFileBridge.kt`) and the bridge-id ⇄ `NSFileProviderItemIdentifier` mapping. Items are
  addressed by a daemon-minted id that survives rename and move — never by path (proposal §5a).
- `TenshuFileProviderItem.swift` — `NSFileProviderItem` mapping; the content version is the
  daemon's, so it moves exactly when the bytes do.
- `TenshuFileProviderEnumerator.swift` — listings from `listFolder` / `listAll` (the working
  set is every item), changes from the daemon's anchor-based feed.
- `TenshuFileProviderExtension.swift` — the principal class: read, write, thumbnails
  (`NSFileProviderThumbnailing`, from the realm's stored thumbnail classes — proposal §5a D4)
  and the change poll.
- `Info.plist` — extension point `com.apple.fileprovider-nonui` + principal
  class.
- `DomainRegistrar.swift` — a **separate** tiny CLI target that registers /
  removes the `NSFileProviderDomain` (the mount + sidebar entry). Drive runs it on
  every launch.

The extension's entitlements are `drive-desktop/macos/entitlements/drive-fileprovider.entitlements`
(app-sandbox + App Group). The JVM host app's App Group plist is generated by `signDesktopApp`.

## Status

Built, signed, embedded and registered by the Gradle build; the domain registers and the mount
appears under `~/Library/CloudStorage/` (2026-10-04). The daemon methods it drives are covered
by desktop tests (`FileBridgeRoundTripTest`, `FileWriteBridgeRoundTripTest`,
`ControlFileBridgeTest`); everything Finder-side is on-device manual.

## Build, embed, sign

One command, on a Mac with `tenshu.teamId` + `tenshu.signingIdentity` configured and XcodeGen
installed:

```bash
./gradlew :drive-desktop:packageDesktopApp
```

`embedFileProviderExtension` generates the Xcode project from `project.yml`, builds the `.appex`
**unsigned**, compiles `tenshu-domain` with swiftc, and embeds them at
`Contents/PlugIns/TenshuFileProvider.appex` and `Contents/MacOS/tenshu-domain`. `signDesktopApp`
then signs the extension with `drive-fileprovider.entitlements` (sandbox + App Group) and
everything else with the host's App Group plist.

Drive registers the domain itself on every launch (`FinderIntegration.kt`); `tenshu-domain
remove` tears it down.

What was measured on 2026-10-04, and what was not:

- ⚠⚠ **`tenshu-domain` only works when Drive spawns it.** Run from a shell it fails with
  `providerNotFound` (-2001 / -2014; `fileproviderd` logs `No provider found … for calling
  bundle`) — from `Contents/Helpers`, from `Contents/MacOS`, from the build directory and from
  `/Applications` alike. Spawned by the running `TenshuDrive.app` it registers. The daemon
  attributes the call to the process *responsible* for the caller, so test registration by
  launching Drive, never by running the helper.
- ⚠ **Even from Drive, the first attempt after an install or update can be refused** with the
  same `providerNotFound`: the system has not re-discovered the extension in the freshly copied
  bundle yet. Seen twice on 2026-10-04, seconds after the copy; Drive retries
  (`FinderIntegration.kt`) and a later attempt in the same launch registered.
- ⚠ **Not established:** whether `Contents/Helpers` would also work when Drive spawns it (from a
  shell the daemon saw `calling bundle (null)` there and a non-null bundle from `Contents/MacOS`,
  which is why it lives in `Contents/MacOS`), and whether a Drive run out of the build directory
  registers while another copy with the same bundle id is installed.
- ⚠ **The first domain came up `user-disabled`** and had to be enabled in System Settings →
  General → Login Items & Extensions → File Providers; until then the mount exists and every
  listing times out. A domain registered later the same day came up enabled, so this may have
  been a consequence of the failed attempts before it rather than the default.
  `fileproviderctl dump app.tenshu.drive.fileprovider` shows the state.

⚠ `log` is a zsh builtin — use `/usr/bin/log show …` or the predicate is rejected with
"too many arguments" and you read an empty log as "nothing happened".

## Manual on-device verification

With a signed `TenshuDrive.app` installed, the Control daemon running, and the
domain registered:

- **Tenshu Drive** appears in Finder's sidebar under *Locations*.
- Navigating folders matches the Drive app (`listFolder`).
- A dataless file shows correct size/dates (`itemMetadata`); double-clicking it
  downloads + opens it (`fetchContents` → `readContents`); eviction returns it to
  dataless.
- Creating a folder, dragging in / editing / renaming / deleting a file in Finder
  round-trips to other devices (`createItem` / `modifyItem` / `deleteItem`); a
  duplicate name surfaces a collision.
- With the daemon stopped, items report unavailable rather than hanging.
- ⚠ **Not yet done for thumbnails:** a dataless image, video and PDF show a picture in icon
  and gallery view **and stay dataless**; a text file shows its type icon; an image whose only
  stored class is an Android-minted WebP shows a picture; replacing a file's content replaces
  its thumbnail.

## When Finder says the provider is unavailable

- **"Server unreachable" is sticky.** After the extension reports it, the system stops calling
  for minutes — so a brief failure looks like a long outage. `fileproviderctl dump
  app.tenshu.drive.fileprovider` shows the last error and the `next:` retry time; the time the
  extension last actually *tried* is in the log (`/usr/bin/log show --predicate 'process ==
  "TenshuFileProvider"'`), not in that dump.
- **The error names the cause.** `BridgeClient` waits ~7 s for a socket nobody is listening on
  yet, then reports the errno: `2` (no socket file — Control is not running; it removes its
  sockets on a clean quit), `61` (refused — a file left by a killed Control, or one still
  starting), `1`/`13` (the sandbox refused).

## Outstanding

- **Thumbnails stop at 256 px** and exist only for files that have a stored class (§5a D4).

- **Remote changes need someone looking.** The extension signals for changes when it starts and
  every 30 s while alive; nothing signals while it is not running (proposal §5a D2).
- **A move made on another device is delete + create here** (§5a D1).
- **Permission posture** (`tenshu-rei.md` §2.2): enforcement is proxy-side and currently ungated.
- **Conflict versions** for concurrent edits.
- **Uploads are held in memory once** by the daemon (the file-service takes a `ByteArray`), and
  are refused above 2 GiB. Downloads are chunked. Contents cross as files in the group
  container's `fileprovider-staging/`, never through the bridge (proposal §5b).
