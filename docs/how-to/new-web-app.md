# How to add a web app

A Tenshu web app is its own pnpm package under `web/<id>/`, served from its own origin
(`<id>.tenshu.app`) and framed by the apex ([ADR 0020](../adr/0020-web-app-structure.md)). It is
built on `@tenshu/app-kit` (`web/app-kit`), and the apex knows it through one registry file. The
background is [`web-app-suite.md`](../proposals/web-app-suite.md) §3 F3/F4.

## 1. Scaffold it

```bash
scripts/new-web-app.sh <id> <port> ["Display Name"]
scripts/new-web-app.sh calendar 5176
```

- `<id>` is the subdomain, the package name, the apex route (`/<id>`) and the `tenshu/app/<id>` app
  id. It must be lowercase letters, digits and hyphens.
- `<port>` is the app's Vite dev server. The apex runs on 5173, Drive on 5174 and Contacts on 5175.
  The script refuses a port another app already uses.

It creates two things and edits no shared file:

| Created | What it is |
|---|---|
| `web/<id>/` | A working app: package, Vite/TS/ESLint configs from the app-kit, a minimal screen with the lease banner, `src/lib/proxy.ts` with only the session methods, i18n en/de/fr, three tests (render, catalogue parity, SDK boundary), and the manifest (generated by the Vite preset from `vite.config.ts`). |
| `web/apex/src/apps/registry/apps/<id>.ts` | The app's apex registry entry: origin, dev port, env name, allowlist, route and the Apps-section entry. **Adding this file is the registration.** The launcher, the Apps list, the `/<id>/*` route and the gateway's origin and allowlist all read the registry. |

It then runs `pnpm install` (the lockfile gains one importer) and prints the checklist below.
Check the result:

```bash
cd web
pnpm -F <id> build && pnpm -F <id> test && pnpm -F <id> lint
pnpm -F apex test      # the registry and allowlist tests now cover <id>
pnpm -F <id> dev       # http://localhost:<port>; run `pnpm -F apex dev` too
```

The web gate (`scripts/run-web-gate.sh`), CI (`.github/workflows/web.yml`) and the image build
(`deploy/build-apex-image.sh`) find the app by themselves. An app is any `web/<id>` that has a
`vite.config.ts` (`deploy/lib/web-apps.sh`).

## 2. What is left by hand

1. **Calls.** Each method the UI calls goes in two places, by its exact name:
   - the `ProxyMethod` table in `web/<id>/src/lib/proxy.ts`, plus a typed wrapper over
     `bridge.call` or `bridge.subscribe`;
   - `methods` in the registry entry. This is the F5 allowlist, and an XSS on the app's origin can
     reach every method on it.

   `gatewayPermissions.test.ts` fails until the two lists agree. `gateway.test.ts` fails if an
   allowed method has no handler. A method in an existing namespace gets its handler in
   `web/apex/src/lib/gateway/<namespace>.ts`. A new namespace needs a new module there plus one
   line in `gateway/index.ts`.
2. **SDK boundary.** This is the first PR of the app's three-PR cut (`web-app-suite.md` §4). After
   the Kotlin `@JsExport` facade, add:
   - `web/sdk/src/native/<svc>.d.ts` and one reference line in `web/sdk/src/native.d.ts`;
   - `web/sdk/src/<svc>.ts`, its `"./<svc>"` entry in `web/sdk/package.json`, and its export in
     `_bundle.ts`.

   ⚠ The app may import `@tenshu/sdk/<svc>` with `import type` only. Every `sdkBoundary.test.ts`
   fails on a value import.
3. **Display data.** Fill in:
   - the permissions and services in the registry entry (marked `TODO`);
   - the manifest's semantic permissions in `web/<id>/vite.config.ts`;
   - optionally, launcher copy under `appLauncher.entries.<id>` in
     `web/apex/locales/{en,de}/control.json`. Without it the launcher shows the registry's English
     label and description.
4. **The app itself.** Use the app-kit for the shared pieces:

   | Need | Use |
   |---|---|
   | Views that read the bridge | TanStack Query, with keys from `defineQueryKeys` |
   | Pushed streams | `useLive` plus `createLiveContext` (Contacts' `LiveProvider`), and `StreamNotice` when a stream dies |
   | Typed failures | `knownErrorKind` / `bridgeErrorKind` (copy by `kind`, never by `message`) |
   | Device sync state | `SyncHealthNotice`, with `sync.health.observe` added to both lists |

## 2b. A map (Maps, Timeline routes, Fit)

A map is `<TenshuMap>` from `@tenshu/map-kit` (`web/map-kit`, web-app-suite.md §4 W-MAP). It draws
`:basemap-core`'s style with MapLibre GL JS, and reads the region archive a range at a time through the
apex (`mapRegion.*`). Never write a style, add a tile source or point at a font CDN in an app.

1. **Dependency.** Add `"@tenshu/map-kit": "workspace:*"` to the app's `package.json` and run
   `pnpm install`.
2. **Glyphs from the app's own origin.** In `web/<id>/vite.config.ts`, add the plugin:

   ```ts
   import { mergeConfig } from 'vite'
   import { tenshuAppConfig } from '../app-kit/src/vite.ts'
   import { tenshuMapGlyphs } from '../map-kit/src/vite.ts'

   export default mergeConfig(tenshuAppConfig({ port, manifest }), { plugins: [tenshuMapGlyphs()] })
   ```

   In dev it serves `/glyphs/<fontstack>/<range>.pbf`. In a build it emits the same files into
   `dist/glyphs/`, plus the font's `OFL.txt`. The source is the native glyph set
   (`ui-map/src/androidMain/assets/glyphs`), so there is no second copy to keep in step. Import it by
   file path, like the app-kit preset, because Node will not strip types under `node_modules`.
   ⚠ `glyphsBase` on `<TenshuMap>` and the plugin's `base` must agree. Both default to `/glyphs`.
3. **Calls.** Add the `MapRegionMethod` names to the app's `ProxyMethod` table **and** its registry
   allowlist (F5), as for any call:
   - `mapRegion.regionAt`;
   - `mapRegion.streamRange`;
   - `mapRegion.regionsIn` and `mapRegion.catalog` only if the app uses them.

   Build the region access from the app's bridge:

   ```tsx
   import { TenshuMap, bridgeRegionAccess } from '@tenshu/map-kit'
   const regions = bridgeRegionAccess(bridge.call)
   <TenshuMap regions={regions} camera={{ kind: 'bounds', points }} polylines={…} pins={…} theme={theme} labels={t(…)} />
   ```

   - The camera takes a centre and zoom, or points to fit. Both are clamped to `BASEMAP_MAX_ZOOM`.
   - Pins are Maps places.
   - Polylines are trips and routes. Each segment has its own `#RRGGBB` colour.
   - `theme` follows the app's theme.
   - Pass `labels` from the app's i18n. The English defaults are for the harness.
4. **Lazy by construction.** Importing `@tenshu/map-kit` does not load MapLibre or pmtiles. They load
   with the first rendered map (`lazySplit.test.ts`). Do not import `maplibre-gl` in the app.
5. **What the user sees when there is no map.**
   - Without WebGL, or while the tile transport is not configured, the map renders an explicit
     "Map unavailable" with the reason.
   - A failed tile shows an alert over the map.
   - A camera outside every region draws the background and says so.

   Tiles stream through the apex runtime's `FetchTileTransport` (W.1). ⚠ Only the FIRST
   region lookup may replace the map with a failure panel; a lookup after a pan stays with map-kit's
   own alert (Timeline's `AppMap`). `pnpm -F @tenshu/map-kit harness` renders the Firenze demo
   extract through the same source, without the bridge.

**CSP.** Hosted apps send only `frame-ancestors` today (`hosted_app` in `web/apex/Caddyfile`). A map
app's site block imports `hosted_map_app` instead (same arguments; Timeline, Maps and Fit use it), which sends
the complete set it needs. Both are one import of `hosted_app_site`, which takes the policy as its
argument, so everything else about the site stays shared. ⚠ It is the standard policy for any app
that uses the shared Dialog, map or not:

```
default-src 'self';
script-src 'self';
style-src 'self';
style-src-elem 'self' 'unsafe-inline';
connect-src 'self';
img-src 'self' data: blob:;
worker-src blob:;
child-src blob:;
frame-src <apex origin>;
frame-ancestors <apex origin>
```

- The map-specific lines are `worker-src blob:`, `child-src blob:` (the fallback older Safari reads
  for workers) and `img-src data: blob:`. MapLibre starts its tile workers from a `blob:` URL and
  decodes images through `data:`/`blob:`.
- `connect-src 'self'` is enough, and nothing should widen it. Glyphs come from the app's own origin.
  Tile bytes arrive through the bridge (`postMessage`), and the app frame never fetches them. The
  apex does that fetching, per W.1.
- `frame-src` is the hidden apex iframe every app already dials.
- ⚠ `'unsafe-inline'` is on `style-src-elem` only, never on `style-src`: the shared Dialog's scroll lock
  (Radix → `react-remove-scroll` → `react-style-singleton`) injects a `<style>` element, and that is
  the one inline style an app needs. React's `style={}` props are set through the CSSOM, which no
  style directive blocks, so style *attributes* stay refused (`style-src-attr` falls back to
  `style-src`). `csp/caddyfile.test.ts` pins the set.
- Checked in headless Chromium: this header on Fit's build, with the shared Dialog open and a
  MapLibre canvas drawn, gives 0 violations; dropping `'unsafe-inline'` from `style-src-elem` gives
  one (the scroll lock's `<style>`). ⚠ Not yet behind Caddy in the dev lab, nor with live tiles.
- Maps run B checked it too, in headless Chromium: the map-kit harness drew the Firenze tiles behind
  this header with no violation, and the Maps shell raised none.

## 3. Ship it to the dev lab (maintainer)

The image build and CI need nothing. These steps are deploy decisions, so the scaffold does not
generate them:

1. **Caddy.** Add a two-line site block in each file:
   - `web/apex/Caddyfile`:
     `{$<ID>_SITE} { import hosted_app <id> "{$<ID>_FRAME_ANCESTORS}" }`
     (keep the quotes; the Caddyfile comment says why). A map app imports `hosted_map_app` instead
     (§2b CSP);
   - `deploy/scaleway-dev/stack/Caddyfile`: `{$<ID>_DOMAIN} { import hosted_app_proxy <id> }`.
   - `web/apex/Caddyfile` again: add `{$<ID>_SITE}` to the apex's own `frame-ancestors` line. Opened
     directly, an app mounts the apex in a hidden iframe, which that line otherwise refuses
     (`csp/caddyfile.test.ts` fails until it is there).
2. **Compose.**
   - In `web/apex/docker-compose.yml`, set
     `<ID>_SITE: "${<ID>_DOMAIN:-http://<id>.disabled.invalid}"` and
     `<ID>_FRAME_ANCESTORS: "https://${APEX_DOMAIN}"`.
     ⚠ The placeholder default is load-bearing. An empty site address is a Caddyfile parse error
     that takes the apex down.
   - In `deploy/scaleway-dev/stack/dev-overlay.yml`, set `<ID>_DOMAIN` on the front Caddy, and
     `<ID>_SITE: "http://<id>.${APEX_DOMAIN}"` plus `<ID>_FRAME_ANCESTORS` on the apex.
3. **DNS.** Create `<id>.tenshu.xyz` in Cloudflare (DNS-only), like the other dev records.
4. **Ship.** Run `deploy/ship-dev-stack.sh root@<dev box> --only apex`. It builds every app for
   `https://<id>.tenshu.xyz` and checks that each bundle contains its partner origin.
5. **Browser pass** against `https://<id>.tenshu.xyz` and the apex at `/<id>`, as in
   `web-app-suite.md` §6.

For production, add `deploy/dns/records.json` for `<id>.tenshu.app` and `<ID>_DOMAIN` in the
production `apex.env`. Until then the app's site stays the `disabled.invalid` placeholder.
