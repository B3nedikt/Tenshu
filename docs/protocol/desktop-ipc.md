# Tenshu Desktop IPC: Unix Domain Sockets

This document outlines the architecture for Inter-Process Communication (IPC) between Tenshu
applications on Desktop (macOS/Linux/Windows).

## 1. Overview

While Android uses the Binder system for cross-app communication, Desktop platforms require a
different approach to bridge the **Tenshu Client** (e.g., Drive) and the **Tenshu Proxy** (e.g.,
Control). We use **Unix Domain Sockets (UDS)** as the primary transport layer.

### Why Unix Domain Sockets?

* **Performance**: Faster than local TCP loopback as it avoids the networking stack overhead.
* **Security**: Access is controlled by filesystem permissions. By placing the socket in a private
  user directory, we prevent other users or network entities from reaching the service.
* **Bidirectional**: Supports full-duplex communication, allowing the Proxy to send real-time
  events (sync updates, notifications) back to the Client.
* **Native JVM Support**: Java 16+ provides first-class support for Unix Domain Sockets via
  `java.nio`.

## 2. Architecture

### The Pipe Model

The communication is based on a "Server-Client" relationship where the Proxy app owns the lifecycle
of the socket.

1. **Control App (Proxy/Server)**:
    * On startup, it creates a socket file at a directory chosen by
      `SocketPathResolver` (`~/.tenshu/ipc.sock` for unsandboxed dev runs; the
      macOS App Group container when signed — see §6).
    * It listens for incoming connections from Tenshu client apps.
    * For every connection, it provides an `ExecutionContext` isolated to that client.

2. **Drive App (Client)**:
    * On `TenshuClient.init()`, it attempts to connect to the socket file.
    * It wraps the socket stream in a `RemoteBinaryTaskExecutor`.

### Framing Protocol

Since sockets are stream-oriented, we use a simple framing header to delineate Tenshu binary
packets:

* **Length**: 4 bytes (big-endian Int) — the length of the payload.
* **Type**: 1 byte — frame kind (`StreamFramer`: response / callback /
  cancellable-request / cancellable-response / cancel / hello / correlated-request /
  correlated-response / correlated-failure — §2.2 for those four — and cancel-read, §2.3).
* **Payload**: The raw bytes generated by `BinarySerializer`.

The same `[length][type][payload]` layout is reused by the JSON native bridge
(§6.2), with a JSON payload instead of binary.

### ⚠⚠ Response routing: the legacy plain path is not correlated

> Since §2.2 a plain `call()` is correlated too, on every connection whose proxy answers the hello.
> ⚠ **The uncorrelated path is gone (1.0.1 re-cut, 2026-11):** no build older than the hello ever
> reached a user, so the client no longer falls back to it and the server no longer serves a plain
> `TYPE_RESPONSE` request (it drops the connection). What follows is the history of why it had to go.

The two request kinds answer a caller in completely different ways, and the difference is a
correctness constraint, not an implementation detail:

* **Cancellable** (`TYPE_CANCELLABLE_REQUEST` → `TYPE_CANCELLABLE_RESPONSE`) carries a
  client-minted task id, echoed back, so the client routes each response to its own waiter.
  Several may be in flight at once.
* **Normal** (`TYPE_RESPONSE`) carries **no id at all**. The client writes the frame and takes the
  next item off one shared `responseQueue`; the only thing tying that item to the request is
  `callLock`, which keeps exactly **one normal request in flight per transport**. The server does
  *not* preserve order — it dispatches every frame on its own coroutine — so this client-side
  invariant is the whole of the guarantee.

Therefore: **a normal request that has been written must always consume its response.** If a caller
abandons the pair after the write, the proxy still answers, the answer sits in the queue unclaimed,
and from that moment every call takes the *previous* call's response — permanently, and silently,
because a well-formed response for the wrong chain deserialises fine.

Abandoning is easier than it looks: `withContext(IO) { writeFrame(...) }` performs the write and
*then* throws on resume if the caller was cancelled meanwhile, so any cancellation around the write
does it. `UnixSocketTaskTransport.call` therefore runs write + take under `NonCancellable`, and
`openConnection` clears the queue so a reconnect cannot inherit the dead connection's answers.
`UnixSocketCancelledCallSkewTest` pins both.

This was a live defect, not a hypothetical: `pagingSource`'s `flatMapLatest` cancels the in-flight
page load on every new `PagingData` generation, so simply opening Drive's Files listing skewed the
queue — page 2 arrived holding page 1's rows and crashed the `LazyColumn` with
`Key "…" was already used`, while a `Maybe.get()` came back as a `TListDto`.

The structural fix — correlation, making mis-delivery unrepresentable rather than merely
unreachable — is §2.2.

### 2.1 ⚠⚠ `NonCancellable` means a dead proxy must be detected, not waited out

`NonCancellable` buys the invariant above at a price: **nothing outside can free that waiter.** So
the one case it cannot survive is the proxy dying *while holding the call* — the reader loop hits
EOF, closes the channel and schedules a reconnect **without putting anything into
`responseQueue`**. Before this was fixed, the caller waited on a producer that would never come:

- its own cancellation could not free it (`NonCancellable`);
- it held `callLock` throughout, so **every later `call()` queued behind it** — the transport was
  wedged, not just the read;
- and nothing threw, so no `catch` anywhere ran and no reachability engine was ever told.

Measured on `UnixSocketProxyDeathTest`'s harness: a live proxy answered in **6 ms**; a proxy that
died mid-call never returned at all, and neither did the unrelated call issued after it.

`call()` therefore waits with `awaitResponseOn(channel)` rather than a bare `take()`, failing once
the channel it wrote on is no longer the live one. ⚠ Keyed on **channel identity**, not
`isConnected`: the reconnect thread can have a new channel up within milliseconds, and a liveness
check would then read `true` while this caller's answer is still owed by a socket that no longer
exists.

⚠ It throws `IllegalStateException` deliberately — the type `RemoteBinaryTaskExecutor` already folds
into a typed `TResult.Failure`. That is the same argument `BinderTaskTransport.asNotConnected` makes
for Android, where the un-mapped `DeadObjectException` sailed past the executor and **killed the
client app** ("`FATAL EXCEPTION … android.os.DeadObjectException` killing Timeline every time an
OOMing Control restarted", 2026-08-03). Map at the transport, where the knowledge is platform-local,
and reuse the fold rather than widening a catch.

⭐ Consequence worth knowing when reading app code: **a dead transport no longer throws past the
executor on either platform.** A repository's `catch (e: Exception)` is not what notices a missing
Control — the `fold(onFailure)` arm is. The broad catch still earns its place for `getService` on an
unregistered schema, for serialize/parse (both outside the executor's own `try`), and for the
caller's own post-processing; and while it exists, a `CancellationException` rethrow must precede it,
because that arm would otherwise swallow the rethrow both executors are careful to make.

### 2.2 ⚠⚠ Correlated plain calls — one lost reply costs one caller (2026-09-30)

**The defect.** §2.1 frees the waiter when the proxy *dies*. It cannot when the proxy stays alive and
one reply is simply never written (an operation that never returns, a `ProxyGateway.call` that throws
— the plain path's `printStackTrace` sends nothing). That caller then holds `callLock` inside
`NonCancellable` forever, and **every later call from the app queues behind it**: every read of
every screen. Photos' Collections read timeout recovers on Android (Binder runs calls concurrently)
but could not on desktop. `UnixSocketLostReplyTest` reproduces it against the
real `UnixSocketServer` + `ProxyGateway` with an operation that never returns — not a cancellable
fake, which is the stand-in that once passed against a fix that could never fire on a device.

**The fix.** A plain `call()` now carries a client-minted **call id**, like `callCancellable` carries
a task id:

| Frame | Direction | Body |
|-------|-----------|------|
| `TYPE_HELLO` (5) | both | `HELLO_BODY` (`0xFF "TNSH"` + wire revision 1) |
| `TYPE_CORRELATED_REQUEST` (6) | client → proxy | `packTagged(callId, request)` |
| `TYPE_CORRELATED_RESPONSE` (7) | proxy → client | `packTagged(callId, reply)` |
| `TYPE_CORRELATED_FAILURE` (8) | proxy → client | `packTagged(callId, reason)` — the gateway threw |

Each call registers its own deferred before the write and removes it in `finally`, so: calls run
concurrently (no `callLock`); a caller's own timeout or cancellation frees it; a reply whose id nobody
waits for any more is **dropped**, never handed to another caller; and a socket death fails every call
waiting on that socket (`failPendingCallsOn`, the correlated twin of `awaitResponseOn`).

⚠⚠ **The call id is a transport tag, never a task id.** The KDoc this replaced assumed the fix meant
routing `call()` through the cancellable path, i.e. registering every call in the gateway's
in-flight registry. It must not: a `taskId` makes `ProxyGateway.call` detach the request from the
client's session, count it towards `inFlightCount` (Android's foreground-service promotion) and join
its saves to a sync lane named after it. The server therefore calls the gateway with
`taskId = null` — byte-for-byte the plain path's semantics — and only the framing changes. That is
what kept this a transport change rather than a gateway one; `UnixSocketLostReplyTest` asserts
`inFlightCount == 0` while a correlated call is outstanding.

> ⚠ **As built since the 1.0.1 re-cut (2026-11):** only the `new|new` and `new|mute` rows below
> survive. A proxy that answers the hello with a plain `TYPE_RESPONSE`, or announces a revision below
> `StreamFramer.WIRE_REVISION_FLOOR` (= 2), is treated like a mute one — the connection is closed
> and the call fails (fail closed); the server closes on a plain `TYPE_RESPONSE` request or any type
> it does not know. `legacyCall`/`WireMode` are deleted; `callLock` survives only to serialise the
> hello. The rows are kept as history.

**Version skew.** The desktop apps and Control are separately installed, so either side can be
older; nothing else about the connection gates the wire. The client therefore negotiates **per
connection** (a reconnect may reach a different build) on its first `call()`, under `callLock` and
`NonCancellable`:

| client | proxy | outcome |
|--------|-------|---------|
| new | new | proxy answers `TYPE_HELLO` from its read loop → correlated calls |
| new | old | the old server's `else` branch serves the hello as a plain request; `HELLO_BODY`'s leading `0xFF` cannot parse as a callstack, so **nothing executes** and the gateway answers a `TYPE_RESPONSE` failure. The client consumes it and falls back to the §2/§2.1 path, unskewed. Cost: one parse failure per connection in that Control's diagnostics |
| old | new | unchanged — an old client never sends types 5–8, and `TYPE_RESPONSE` is still served |
| new | mute | no answer within `HELLO_TIMEOUT_MS` (10 s) → the client **closes the connection** and fails the call; the reconnect loop negotiates afresh |

Why the mute case closes rather than guesses: "legacy" would let a late plain reply skew the next
call, "correlated" would send an older proxy frames it reads as garbage. A closed socket makes any
late answer undeliverable. Why negotiation holds `callLock` in `NonCancellable`: the old proxy's
answer lands in the uncorrelated queue, so no legacy call may be waiting on it and the negotiator may
not abandon it. `UnixSocketWireNegotiationTest` pins all four rows, including the real parser's
refusal of `HELLO_BODY`.

⚠ **Residual.** Against an older Control the fallback keeps §2's serialised path and so keeps the
wedge; it goes away as that Control updates. Deleting the fallback (and `callLock`) is a decision
about the oldest supported desktop Control, not a code question. ⚠ `callCancellable` still does not
fail its waiter on proxy death — the same sweep would close it, but it is not this defect.

### 2.3 Cancellable reads — `TYPE_CANCEL_READ` (wire revision 2, 2026-10-01)

§2.2 frees a caller that abandons a correlated call, but Control never hears of it and walks the read
to the end. `core-background-processing.md` §6.2.1 has the diagnosis and the decision; this is the
desktop wire.

| Frame | Direction | Body |
|-------|-----------|------|
| `TYPE_HELLO` (5) | both | `helloBody(revision)` — this build sends **2** |
| `TYPE_CANCEL_READ` (9) | client → proxy | the call id (UTF-8) of a correlated request on **this** socket. No reply |

- The server passes every correlated request's call id to `ProxyGateway.call` as its `readId`, keyed
  by the socket (`readOwner = ch`). That only makes the call *findable*; a call is stopped only by a
  `TYPE_CANCEL_READ` naming it, which the client sends for a `cancellableReads { }` call alone —
  never for a plain one, so a write is never stopped by this frame. A stopped read gets **no reply**:
  its waiter is already gone, and a reply would be dropped anyway.
- The client sends the cancel when the caller is cancelled while the reply is still owed, on the
  socket the request went out on, best-effort.
- ⚠⚠ **Only to a proxy whose hello announced revision ≥ 2.** A revision-1 Control (§2.2) serves any
  type it does not know as a plain request: a type-9 frame would reach `ProxyGateway.call` as a
  callstack to parse, and its `TYPE_RESPONSE` failure would land in the uncorrelated queue.
  `StreamFramer.helloRevision` reads anything that is not a well-formed hello as revision 1, never
  higher.

⚠ Since the 1.0.1 re-cut revision 2 is the floor: the client refuses a lower hello, so only the
first row below is live.

| client | proxy | a cancelled read |
|--------|-------|------------------|
| rev 2 | rev 2 | stops in Control (`CancellableReadTest.socket_*`) |
| rev 2 | rev 1 | correlated call, no cancel frame sent; Control finishes it, as before |
| rev 2 | legacy | §2/§2.1 serialised path, as before |
| rev 1 / legacy | rev 2 | never sends type 9; served exactly as before |

## 3. Security & Handshake

To ensure that only authorized Tenshu apps can talk to the Proxy:

* **FS Permissions**: the socket directory is `700` — owner only, which blocks both cross-user
  `connect()` and cross-user squatting of the socket path. `SocketDirectory.prepare` creates it
  that way and **repairs an existing one**; both servers call it on start. ⚠ The repair is the
  half that matters: until 2026-08-21 this section described a `700` nothing in the code set, so
  a `~/.tenshu` created under the usual umask is `0755` on every machine the old code ran on.
  ⚠ Permissions on the socket *inode* are not a substitute — macOS/BSD ignore them for
  `connect()`, so the directory is the only portable filesystem gate. Either way this bars other
  *users*, never a same-user process: that is the handshake's job.
* **The client checks it too**, because nothing authenticates the *server*: this transport
  connects to a path, so the directory's mode is its only evidence that the socket was placed
  there by the user's own daemon. `SocketDirectory.inspect` grades it — a directory another user
  can **write** to is a refusal (that is the squatting vector), while world-writable-but-sticky
  (`/tmp`) and merely-traversable (`0755`) warn. A directory owned by another user is refused,
  **except root's**: root can replace anything whatever the mode, so owning `/tmp` grants it
  nothing new. ⚠ Without that exception the sticky carve-out never ran, because `/tmp` is root-owned
  on Linux, and every Unix-socket test failed on a Linux CI runner while macOS (whose `$TMPDIR`
  the user owns) passed. ⚠ Warning rather than refusing on `0755` is
  deliberate: the daemon repairs the mode on start and the reconnect loop retries, so a user
  carrying an old directory self-heals instead of being locked out.
* **Handshake — as built (macOS; see the platform note below)**:
    1. Client connects to the socket.
    2. Before a single frame is served, the proxy reads the peer's **audit token**
       (`LOCAL_PEERTOKEN`) and hands it to `SecCodeCopyGuestWithAttributes`, yielding a
       `SecCodeRef` for the peer's **running code**. That code is checked against a
       requirement pinning `anchor apple generic` + a first-party Team ID + the identifier
       the peer's own signature carries (read first as an untrusted *hint*, only to select
       which requirement must hold).
       ⚠⚠ Deliberately **not** PID → binary path → `SecStaticCode`: a pid is reusable, and a
       static check inspects the file on disk rather than the running image
       ([`desktop-ipc-client-identity.md`](../proposals/desktop-ipc-client-identity.md) D2).
    3. The attested identifier **is** the session identity. There is no "Hello" block and the
       client never states its own `AppId` — a peer that fails the check is rejected and its
       channel closed (`strict = true`), or, under developer mode (A16), admitted under a
       unique `unattested-…` id that resolves to no app (fail closed into *anonymous*, never
       into a fallback identity).
    4. A second, independent gate: the attested id must appear in the static allowlist
       (`BundledAppCatalogue`) to be **registered**. ⚠ It does not gate *access* — any
       admitted peer can call anything; see item #5 of the same audit.

  ⚠⚠ **macOS only.** `SO_PEERCRED` (Linux) and `GetNamedPipeClientProcessId` (Windows) are the
  intended equivalents and are **not implemented**: on those platforms every peer resolves
  unattested, so a packaged build would admit no one and a dev run admits everyone. Shipping is
  macOS-only today (`targetFormats(Dmg, Pkg)`). See
  [`docs/proposals/tenshu-rei.md`](../proposals/tenshu-rei.md) §5.F.49 for the longer-term
  edge cases (dev-build bypass, signature-cache invalidation on app update, Windows peer-PID
  race window).

## 4. Platform Compatibility

* **macOS/Linux**: Uses standard Unix Domain Sockets.
* **Windows**: Uses **Named Pipes**, which follow the same stream-based API in Java `nio`, ensuring
  the Kotlin code remains almost identical.

## 5. Implementation Strategy (⚠ historical — this shipped)

⚠ Kept as the original plan. The class is `UnixSocketTaskTransport` (there is no
`UnixSocketTransport`); the server side is `UnixSocketServer` in `core-common/desktopMain`, and
§2 describes the as-built behaviour.

### core-common

* Implement `UnixSocketTransport` using `java.nio.channels.SocketChannel`.
* Implement a `StreamFramer` to handle the length-prefixing.

### control-desktop (Proxy side)

* Add a background service that starts the `ServerSocketChannel` bound to
  `StandardProtocolFamily.UNIX`.

### drive-desktop (Client side)

* Configure Koin to use the `UnixSocketTransport` in the `TaskExecutor` instead of the Android
  Binder bridge.

## 6. macOS App Group socket path & the native bridge

These two additions support the macOS desktop integration (Control tray + Drive
File Provider). Full design:
[`docs/proposals/desktop-macos-integration.md`](../proposals/desktop-macos-integration.md).

### 6.1 Socket-path resolution (`SocketPathResolver`)

A macOS File Provider extension is **sandboxed** and cannot reach an arbitrary
path such as `~/.tenshu/ipc.sock`. The daemon therefore hosts its sockets inside
an **App Group container** shared with its native clients:

```
~/Library/Group Containers/<TEAMID>.app.tenshu.shared/{ipc.sock,bridge.sock}
```

`SocketPathResolver` (`:core-common` desktopMain) picks the directory, first
match wins:

1. explicit directory override — `-Dtenshu.ipc.dir` / `$TENSHU_IPC_DIR` (tests, dev);
2. macOS **with a Team ID** (`-Dtenshu.ipc.teamId` / `$TENSHU_TEAM_ID`, set by the
   signed bundle) → the App Group container above;
3. otherwise → `~/.tenshu` (unsigned dev default; the only option on Linux).

The group container is for sandbox **reachability, not a security boundary** — a
same-user process can still reach the directory. The gate remains the §3
handshake — ⚠ which is an **audit-token** attestation of the running image, explicitly *not*
the "PID → resolve binary → `SecStaticCode`" shape this sentence used to describe (§3 D2: a pid
is reusable, and a static check inspects the file on disk rather than the running image). Signing the
daemon with the `com.apple.security.application-groups` entitlement is handled by
the `:control-desktop:signControlAppForAppGroup` Gradle task.

### 6.2 Native bridge (JSON-over-UDS)

The binary `BinarySerializer` framing (§2 Framing Protocol) is impractical to reimplement in
Swift. Alongside the binary `UnixSocketServer`, the daemon runs a
`NativeBridgeServer` on a **separate** group-container socket (`bridge.sock`)
that speaks a small, stable, **private** JSON request/response protocol; its
handlers translate into real `ProxyGateway` / service calls JVM-side. Native
clients (tray, File Provider) speak JSON and stay minimal; the daemon owns the
mapping to the binary protocol and the permission checks.

* **Framing**: identical to the binary transport — `StreamFramer.frame` →
  `[4-byte BE length][1-byte type][payload]` — so a native client reuses one
  framing routine. Payload is a UTF-8 JSON object.
* **Envelope** (versioned by `NativeBridgeServer.PROTOCOL_VERSION`):
    * Request:  `{"v":1,"id":"<client-string>","method":"<name>","params":{…}}`
    * Success:  `{"v":1,"id":"<echoed>","result":{…}}`
    * Error:    `{"v":1,"id":"<echoed>","error":{"code":"<code>","message":"<text>"}}`
* **Methods (current)**:
    * `ping` — liveness (built in).
    * `getSyncState` — `{state: ACTIVE|LOCKED|DISABLED, enabled, setUp, locked,
      lastSyncTimestamp, deviceId, ownerId, divergenceWarning}` (from `SyncManager`).
    * `openControlWindow` / `quitApp` — show the Control window / quit the daemon
      (slice 1A, backed by `WindowController`).
    * `listApps` — `{apps: [{appId, name, iconName, version, verified,
      deviceCount, installedAt, installedOnThisDevice, registered}]}`. Registered
      apps (from `AppRegistry`) first, then first-party macOS apps that have never
      connected, as `registered: false` launch *candidates* — the daemon does not
      claim they are on disk; the tray asks LaunchServices.
    * `recentNotifications(limit)` — `{notifications: [{id, timestamp, kind,
      name, otherCount?}]}` where `kind` is a stable event code the native side
      renders (slice 1B; `NotificationMapper`).
    * `launchApp(appId)` — launches the app's macOS bundle via LaunchServices
      (`open -b`); the reverse-DNS `appId` doubles as the bundle id for first-party
      apps (`app.tenshu.drive`). `{launched: true}` on success; `not_found` when no
      such bundle is installed (Phase 4 packaging).
    * **File Provider — read** (`registerFileMethods`). Items are addressed by a
      daemon-minted **`id`** that survives rename and move, never by path
      (`desktop-macos-integration.md` §5a); `"root"` is the realm root.
      ⚠ On the wire every File Provider method is named `fileProvider.v2.<name>`: the
      version lives in the name so a Control and a Drive from different releases fail
      each call cleanly (`unknown_method`) instead of reading paths as ids.
      `listFolder(id)` → `{items: [{id, parentId, name, isFolder, size, created,
      modified, category, contentVersion}]}`, `itemMetadata(id)` → `{item: {…}}`,
      `readContents(id)` → `{data: <base64>, encoding, size}` (**decrypted** bytes),
      `thumbnail(id, width, height)` → `{available: true, data: <base64>, encoding, size}`
      (a stored thumbnail class, JPEG/PNG/WebP — never the file's content) or
      `{available: false}` when the realm has none,
      `listAll()` → `{items, anchor}`, `currentAnchor()` → `{anchor}`,
      `changesSince(anchor)` → `{expired, anchor, updated: [item], deleted: [id]}`.
    * **File Provider — write** (`registerFileWriteMethods`):
      `createFolder(parentId, name)`, `createFile(parentId, name, data)`,
      `modifyContents(id, data)`, `moveItem(id, parentId, name)`, `deleteItem(id)`.
      Create/modify/move return the post-write `{item}`; `data` is base64
      **plaintext**; a name collision returns the `already_exists` error code, and a
      move the file-service only deferred returns `unavailable`.
    * **File Provider — contents by hand-off** (`desktop-macos-integration.md` §5b):
      `fetchContents(id, staged)` → `{staged, size}` writes the **decrypted** contents to the
      file `staged` in the group container's `fileprovider-staging/`; `createFileFrom(parentId,
      name, staged)` and `modifyContentsFrom(id, staged)` consume a file the caller put there;
      `cancelTransfer(staged)` stops a fetch. `staged` is a token (`[A-Za-z0-9-]{8,64}`), never a
      path. No file bytes cross the socket; an upload too large for the file-service returns
      `too_large`.
* **Deferred / later phases**: `subscribeSyncState` (push — the tray polls
  `getSyncState` for v1; see the proposal's Phase 1 deviation note); a bounded-memory
  **upload** (downloads are, since §5b; the file-service's upload still takes one `ByteArray`).
