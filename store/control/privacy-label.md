# Tenshu Control (iOS) — App Store privacy label answers

⚖️ **For counsel review before it is entered.** App Store Connect → App Privacy has no public API
(design §2.3), so these answers are typed into the console by hand; this file is the reviewed source
for that, and it sits beside `control-ios/Resources/PrivacyInfo.xcprivacy` so a change to one shows
up in review next to the other. The two must agree (`docs/how-to/ios-testflight.md` §4).

Derived from the code on 2026-10-15. "Collected" in Apple's sense: sent off the device and readable by
us (or a partner) for longer than it takes to answer the request. End-to-end encrypted data the relay
cannot read is treated as not collected (House Rule 1) — ⚖️ that reading of Apple's definition is
the first thing to confirm.

## Tracking

**No.** No advertising or analytics SDK, no IDFA, no App Tracking Transparency prompt, no
`identifierForVendor`.
Source: `PrivacyInfo.xcprivacy` (`NSPrivacyTracking` false, no tracking domains); no Sentry, Firebase,
Crashlytics or analytics dependency in `control-ios` or the `tenshu-sdk-ios*` modules (SKIE's own
analytics is off: the root `build.gradle.kts`, "iOS app frameworks").

### Not collected, and why

- **User Content / everything in the realm.** Encrypted on the device before upload; the relay stores
  ciphertext only. `AGENTS.md` House Rule 1; `docs/sync/threat-model.md` invariant I1.
- **Keys and the recovery phrase.** Made and kept on the device; pairing passes them sealed for the
  new device. Threat model A1, A4, A9.
- **Diagnostics.** `:diagnostics` is device-local; it has no upload path (`diagnostics/.../LogItem.kt`,
  "future opt-in"). No crash reporter is linked.
- **Purchases / Financial Info.** iOS Control has no purchase flow: `control-ios/Sources/ServicesView.swift`
  ("deliberately NO purchase affordances"). Only the free plan via email sign-in. ⚠ This answer changes
  the day in-app purchase ships (`commerce-accounts-and-sessions.md` Ph4b).
- **Location, Contacts, Health, Photos.** Not used: no CoreLocation, Contacts or HealthKit;
  `scripts/ios-archive.sh` `allowed_sensitive_for` keeps the linked set from growing. The camera
  (`NSCameraUsageDescription`, `control-ios/project.yml`) scans a pairing QR code on the device; no
  image leaves it. Face ID is answered by the system; nothing reaches the app but yes or no.

## ⚖️ Open — answers that need a decision before they are entered

1. **The IP address at registration.** Every `/register` writes an `acceptance` row with the client IP
   (`commerce-service/.../routing/AccountRouting.kt`, `CommerceDatabase.kt` `acceptance.ip`), linked to the
   account, as the record of the terms acceptance, and no code deletes it. Apple has no "IP address"
   type; whether it must be declared (and under which type and purpose — App Functionality or "Other")
   is counsel's call. If yes, `PrivacyInfo.xcprivacy` changes with it.
2. **Device ID.** The relay keeps each device's id and public key per realm (`RelayDatabase.kt`
   `device`), readable by us and linked to the realm. They are generated by Tenshu, not the
   hardware's identifiers. Our reading: "User ID"/App Functionality already covers them; Apple's
   "Device ID" means a device-level identifier such as the advertising identifier.
3. **Metadata the relay sees** (how much is stored, how many devices, when they sync — threat model
   A6, T-T-07). Our reading: part of providing the service, not "Product Interaction" usage data.
4. **Server access logs.** Caddy in front of the relay and of commerce logs requests (with client IPs)
   to stdout, kept by size (Docker's 50 MB × 5), not by time. Not verified field by field.
